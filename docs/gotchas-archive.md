# Gotchas Archive — Resolved Production Incidents

Historical context for incidents whose fix has been stable in production. Preserved here (not in `replit.md`) so the working file stays focused on Active gotchas + Stable invariants. If you're debugging a regression, scan this file for similar past symptoms before assuming a brand-new bug.

For active issues and load-bearing rules, see `replit.md` → Gotchas.

---

- **Embedded-PDF Dedup for Imposition** (`server/robust-pdf-generator.ts:~1531`): pdf-lib's `embedPdf` does NOT deduplicate — calling it once per canvas element creates N independent XObjects. With the imposition tool replicating a logo 20-40 times this used to bloat the output PDF past Odoo's nginx ~40 MB limit (silent ECONNRESET on `/artwork/api/attach-pdf` → order with no artwork, e.g. SO89283 / gemma@portwest.ie / CBRE Front Logo). Cache key = `(pdfDoc × sha1(logoPdfBytes))` via a `__embeddedPdfCache` Map stashed on the pdfDoc. Identical sources are embedded once and reused for every placement.

- **Server PDF-Gen Timeout for Large Imposition** (`server/routes.ts:~8321`): the `add-to-cart` flow proxies to `/api/projects/:id/generate-pdf` with a `pdfGenController` AbortController. The timeout was 60 s and fired exactly when 100+ element large-format DTF imposition jobs were finishing — observed in production: SO89576 / Mayo co co (180 elements × `dtf_next_day`, render took 64 s) → `AbortError` → `serverPdfBuf` undefined → `sourceBuf` undefined → `compressUntilFits` block skipped → order added to cart with NO artwork and NO warning. Bumped to 180 s. Also added a `❌❌❌ NO PDF SOURCE` error log for the defensive `else` branch so any future "no source" regression is visible in deployment logs instead of silent.

- **Inline-First PDF Compression** (`server/routes.ts:~8289` `compressUntilFits`): the canvas-based `add-to-cart` flow now escalates compression /prepress → /ebook → /screen in-line BEFORE deciding to offload to `attach-pdf`. Offload only happens if even /screen can't get the payload under `PDF_INLINE_MAX_CHARS` (~40 MB base64). Reason: `/artwork/api/attach-pdf` 404s with empty body for some iframe/customer combinations regardless of payload size (observed: SO89393 / MMC DTF / `teemaster@serigraf.com` — all four 0.5 MB attempts → HTTP 404 → order with no artwork, even after we mirrored the X-Partner-Email header). DTF Quick Upload (`/api/quick-upload-dtf`) was already inline-only and works for these customers; this brings the canvas flow to parity. /ebook + /screen routinely shrink raster-heavy DTF files by >99 % (e.g. 123 MB → 0.4 MB), so almost everything can be inlined.

- **Attach-PDF Resilience Ladder** (`server/routes.ts:~8390`, fallback only): now reached only when the inline escalator can't fit the PDF. Never warns the customer (which would tempt re-adding and duplicate the order). MUST mirror `add-to-cart` request headers — both `Cookie` AND `X-Partner-Email` (iframe sessions can't propagate cross-origin cookies). Pre-shrink: if the offloaded payload exceeds a 32 MB safe cap we compress with `/ebook` (and `/screen` if still too big) before attempt-1. Then 4-attempt escalation: original payload → 1.5 s wait + retry → re-compress with Ghostscript `/ebook` → re-compress with `/screen`. `compressPdfBuffer(buf, mode)` accepts `'prepress'|'ebook'|'screen'`. Last-ditch failure logs `❌❌❌ ATTACH-PDF EXHAUSTED` for monitoring only.

- **Silent Embed Skips on Page 1** (`server/robust-pdf-generator.ts:~671` element loop, `~1859` embedLogoInPages catch): two paths used to silently drop a canvas element from production PDF page 1 — (a) `data.logos.find(l => l.id === element.logoId)` returning undefined fell off the end of `if (logo)` with no else, only a quiet `Logo not found` debug line; (b) any throw inside `embedLogoInPages` (cropPdfToContentBounds, fs.readFileSync, embedPdf, drawPage) was caught and logged once as `❌ Failed to embed logo` then the loop continued. Symptom in production: SO89550 / UVMAKTUS / uv_dtf_A3 / 4 logos × 15 elements rendered in only 10 s with a single `📥 Embedded new PDF source` event in logs and zero `♻️ Reusing cached` events — page 1 shipped largely empty while the canvas-screenshot final page showed the full layout. Now: (a) loud `❌❌❌ ELEMENT DROPPED — logoId not in project logos` with the missing logoId AND the available logoIds for diagnosis; (b) loud `❌❌❌ EMBED THREW` with element + logo context + stack on each catch; outer loop checks a per-pdfDoc `__embedSuccessCount` counter and retries the embed ONCE before recording the skip; post-loop `📊 EMBED SUMMARY` always logs attempted/embedded/skipped counts and `❌❌❌ PAGE-1 EMBED INCOMPLETE` fires whenever the PDF leaves with fewer logos than placed. Per user preference no customer-facing warning is added (would tempt re-add → duplicate orders); detection is server-side via deployment logs only. The success counter must be bumped from EVERY drawing path — both `drawPage` (PDF embed) and `drawImage` (raster `embedRasterImage` early-return) — otherwise raster elements look like silent failures and trigger pointless retries.

- **Aspect-Ratio Auto-Crop Top-Left Assumption** (`server/robust-pdf-generator.ts:~1539`): when source PDF page is larger than the canvas element AND aspect ratios differ AND the logo has no `originalPdfBounds` stored, the OLD code derived a crop assuming content sat at the top-left corner of the page (`xMin=0, yMin=pdfH-elemH, xMax=elemW, yMax=pdfH`). For source PDFs whose content was NOT in the top-left, this silently dropped everything outside that rectangle. Production case: SO89526 / Wilton Orange Hi Vis Back / SRA3 / 39-tile imposition — source was a multi-page reorder PDF (3 pages: artwork, metadata, canvas screenshot), pass-through mode skips upload-time bbox detection so `originalPdfBounds` is empty. Page 1 artwork had a blue WILTON square on the LEFT and an orange rectangle extending to the RIGHT; the top-left crop captured only the blue portion → production PDF page 1 showed 39 blue squares with NO orange backgrounds, while canvas screenshot (page 2 of output) showed the full design including orange. Now: when no stored bounds, run `gs -sDEVICE=bbox` LIVE on the source PDF; only crop when detection returns reasonable bounds (positive size, fits on page, ≥5% of page area). On detection failure or suspect bounds, SKIP cropping entirely and embed the full page (letter-boxed inside the element) — letter-boxing is a visible, recoverable error; silent content loss is not. Loud `❌❌❌ AUTO-CROP SKIPPED` logs include `logoPdfPath`, element id, and logo id for diagnosis.

- **DTF Quick Upload Single-Tier Compression** (`server/routes.ts:~10455` `/api/quick-upload-dtf`): the OLD code only ran Ghostscript `/prepress` with `-dDownsample*=false`, which barely shrinks raster-heavy DTF (the same 105 MB `AFRICA DAY CT DTF ART.pdf` from enda@tees.ie that crashed the canvas flow ALSO crashed Quick Upload — `/prepress` left it close to original size, the giant base64 string stayed in memory through `JSON.stringify(requestBody)` which makes another full copy of `pdfBase64`, RSS hit 400+ MB, watchdog killed in-flight request → no order). Now: escalate `/prepress → /ebook → /screen` until base64 length ≤ `DTF_MAX_BASE64` (40 MB). After successful shrink, set `req.body.pdfBase64 = undefined` and hint `global.gc()` so the original 100+ MB string is reclaimable BEFORE the next big allocation (the JSON-stringified Odoo request body). Same temp-naming convention as `preShipCompress` (`dtf_gen_in_…`/`dtf_gen_out_…` with random+pid suffix) so the index.ts sweeper picks up any leftovers.

- **OOM Watchdog vs Large PDF Generation** (`server/routes.ts:~1643` post-generation in `/api/projects/:id/generate-pdf`): the memory watchdog at `server/index.ts:131-212` triggers a graceful `process.exit(1)` 3 s after RSS exceeds `MEMORY_RESTART_MB=400`. The robust generator path then does TWO memory-doubling steps before responding: (1) `appendCanvasScreenshotPage` re-loads the buffer into pdf-lib and copies all XObjects, (2) `res.send` queues another Buffer copy in the response stream. Production case: enda@tees.ie / `AFRICA DAY CT DTF ART.pdf` / large_dtf and daragh@hairybaby.com / large_dtf — 105 MB raw PDF pushed RSS to 507 MB, watchdog killed the process before add-to-cart's `compressUntilFits` could ever run → no order, no error, no fallback. Fix: when the generated buffer exceeds 30 MB, run Ghostscript `/ebook` (escalating to `/screen` if still huge) IMMEDIATELY after `generator.generatePDF()` returns, before screenshot append. Raster-heavy DTF compresses >99 % (123 MB → 0.4 MB), so post-compression RSS stays well under the 400 MB ceiling for the rest of the request. Hint `global.gc()` after swap to free the original buffer. Loud `🛟 Pre-ship compression` logs make this visible in deployment logs. Do NOT raise `MEMORY_RESTART_MB` — the watchdog protects against actual OOM-kill by the container; treating the symptom keeps the source memory leak hidden. (Now paired with the **OOM Watchdog Self-Cancelling on Recovery** active gotcha in `replit.md` — when pre-ship compression DOES run but the watchdog has already armed during the un-compressed phase, the recovery check aborts the exit.)

- **Orientation Auto-Switch Uses Source, Not Scaled Element** (`client/src/pages/upload-tool.tsx:~389-525`): the auto-switch between portrait/landscape template variants (e.g. `uvdtf-A3` ↔ `uvdtf-A3-landscape`) MUST compare the LOGO's natural source dimensions (`logo.originalWidth` / `logo.originalHeight`, mm pre-scaling), NOT the canvas element's `width`/`height`. Reason: by the time the orientation effect runs, fit-to-bounds has already scaled the canvas element down — e.g. an A3 landscape PDF (420×297mm) dropped on portrait `uv_dtf_A3` (297×420mm) gets fit-to-bounds scaled to ~217×228mm (slightly taller than wide), which then looks PORTRAIT and matches the portrait template → no switch fires → user sees landscape artwork clipped on a portrait canvas (production: ennis safety / info@esw.ie / esw_eastern_electrical.pdf — user manually rotated 90° + dragged off-canvas trying to recover, then deleted the upload). v1 fix used originalWidth/originalHeight as PREFERRED but fell back to canvas-element dims, which still hit this trap whenever the upload mutation's onSuccess returned the logo record before the deferred `storage.updateLogo` (with originalWidth/Height from PDF MediaBox at routes.ts:~6382) had landed in the React Query cache. v2 (current) REQUIRES `logo.originalWidth && logo.originalHeight` — no element-dim fallback. While waiting, an `orientationCheckTick` state + 400ms `setTimeout` retriggers the effect; a 6s `pendingOrientationCheckStartedAtRef` timeout gives up rather than wedging the pending list. Also added a "source large enough that orientation matters" guard (longest source side ≥60% of template's longest side) so a tiny portrait logo on a landscape canvas doesn't churn the template.
