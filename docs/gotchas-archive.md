# Gotchas Archive — Resolved Production Incidents

Historical context for incidents whose fix has been stable in production. Preserved here (not in `replit.md`) so the working file stays focused on Active gotchas + Stable invariants. If you're debugging a regression, scan this file for similar past symptoms before assuming a brand-new bug.

For active issues and load-bearing rules, see `replit.md` → Gotchas.

---

- **Embedded-PDF Dedup for Imposition** (`server/robust-pdf-generator.ts:~1531`): pdf-lib's `embedPdf` does NOT deduplicate — calling it once per canvas element creates N independent XObjects. With the imposition tool replicating a logo 20-40 times this used to bloat the output PDF past Odoo's nginx ~40 MB limit (silent ECONNRESET on `/artwork/api/attach-pdf` → order with no artwork, e.g. SO89283 / gemma@portwest.ie / CBRE Front Logo). Cache key = `(pdfDoc × sha1(logoPdfBytes))` via a `__embeddedPdfCache` Map stashed on the pdfDoc. Identical sources are embedded once and reused for every placement.

- **Server PDF-Gen Timeout for Large Imposition** (`server/routes.ts:~8321`): the `add-to-cart` flow proxies to `/api/projects/:id/generate-pdf` with a `pdfGenController` AbortController. The timeout was 60 s and fired exactly when 100+ element large-format DTF imposition jobs were finishing — observed in production: SO89576 / Mayo co co (180 elements × `dtf_next_day`, render took 64 s) → `AbortError` → `serverPdfBuf` undefined → `sourceBuf` undefined → `compressUntilFits` block skipped → order added to cart with NO artwork and NO warning. Bumped to 180 s. Also added a `❌❌❌ NO PDF SOURCE` error log for the defensive `else` branch so any future "no source" regression is visible in deployment logs instead of silent.

- **Inline-First PDF Compression** (`server/routes.ts:~8289` `compressUntilFits`): the canvas-based `add-to-cart` flow now escalates compression /prepress → /ebook → /screen in-line BEFORE deciding to offload to `attach-pdf`. Offload only happens if even /screen can't get the payload under `PDF_INLINE_MAX_CHARS` (~40 MB base64). Reason: `/artwork/api/attach-pdf` 404s with empty body for some iframe/customer combinations regardless of payload size (observed: SO89393 / MMC DTF / `teemaster@serigraf.com` — all four 0.5 MB attempts → HTTP 404 → order with no artwork, even after we mirrored the X-Partner-Email header). DTF Quick Upload (`/api/quick-upload-dtf`) was already inline-only and works for these customers; this brings the canvas flow to parity. /ebook + /screen routinely shrink raster-heavy DTF files by >99 % (e.g. 123 MB → 0.4 MB), so almost everything can be inlined.

- **Attach-PDF Resilience Ladder** (`server/routes.ts:~8390`, fallback only): now reached only when the inline escalator can't fit the PDF. Never warns the customer (which would tempt re-adding and duplicate the order). MUST mirror `add-to-cart` request headers — both `Cookie` AND `X-Partner-Email` (iframe sessions can't propagate cross-origin cookies). Pre-shrink: if the offloaded payload exceeds a 32 MB safe cap we compress with `/ebook` (and `/screen` if still too big) before attempt-1. Then 4-attempt escalation: original payload → 1.5 s wait + retry → re-compress with Ghostscript `/ebook` → re-compress with `/screen`. `compressPdfBuffer(buf, mode)` accepts `'prepress'|'ebook'|'screen'`. Last-ditch failure logs `❌❌❌ ATTACH-PDF EXHAUSTED` for monitoring only.

- **Silent Embed Skips on Page 1** (`server/robust-pdf-generator.ts:~671` element loop, `~1859` embedLogoInPages catch): two paths used to silently drop a canvas element from production PDF page 1 — (a) `data.logos.find(l => l.id === element.logoId)` returning undefined fell off the end of `if (logo)` with no else, only a quiet `Logo not found` debug line; (b) any throw inside `embedLogoInPages` (cropPdfToContentBounds, fs.readFileSync, embedPdf, drawPage) was caught and logged once as `❌ Failed to embed logo` then the loop continued. Symptom in production: SO89550 / UVMAKTUS / uv_dtf_A3 / 4 logos × 15 elements rendered in only 10 s with a single `📥 Embedded new PDF source` event in logs and zero `♻️ Reusing cached` events — page 1 shipped largely empty while the canvas-screenshot final page showed the full layout. Now: (a) loud `❌❌❌ ELEMENT DROPPED — logoId not in project logos` with the missing logoId AND the available logoIds for diagnosis; (b) loud `❌❌❌ EMBED THREW` with element + logo context + stack on each catch; outer loop checks a per-pdfDoc `__embedSuccessCount` counter and retries the embed ONCE before recording the skip; post-loop `📊 EMBED SUMMARY` always logs attempted/embedded/skipped counts and `❌❌❌ PAGE-1 EMBED INCOMPLETE` fires whenever the PDF leaves with fewer logos than placed. Per user preference no customer-facing warning is added (would tempt re-add → duplicate orders); detection is server-side via deployment logs only. The success counter must be bumped from EVERY drawing path — both `drawPage` (PDF embed) and `drawImage` (raster `embedRasterImage` early-return) — otherwise raster elements look like silent failures and trigger pointless retries.

- **Aspect-Ratio Auto-Crop Top-Left Assumption** (`server/robust-pdf-generator.ts:~1539`): when source PDF page is larger than the canvas element AND aspect ratios differ AND the logo has no `originalPdfBounds` stored, the OLD code derived a crop assuming content sat at the top-left corner of the page (`xMin=0, yMin=pdfH-elemH, xMax=elemW, yMax=pdfH`). For source PDFs whose content was NOT in the top-left, this silently dropped everything outside that rectangle. Production case: SO89526 / Wilton Orange Hi Vis Back / SRA3 / 39-tile imposition — source was a multi-page reorder PDF (3 pages: artwork, metadata, canvas screenshot), pass-through mode skips upload-time bbox detection so `originalPdfBounds` is empty. Page 1 artwork had a blue WILTON square on the LEFT and an orange rectangle extending to the RIGHT; the top-left crop captured only the blue portion → production PDF page 1 showed 39 blue squares with NO orange backgrounds, while canvas screenshot (page 2 of output) showed the full design including orange. Now: when no stored bounds, run `gs -sDEVICE=bbox` LIVE on the source PDF; only crop when detection returns reasonable bounds (positive size, fits on page, ≥5% of page area). On detection failure or suspect bounds, SKIP cropping entirely and embed the full page (letter-boxed inside the element) — letter-boxing is a visible, recoverable error; silent content loss is not. Loud `❌❌❌ AUTO-CROP SKIPPED` logs include `logoPdfPath`, element id, and logo id for diagnosis.

- **DTF Quick Upload Single-Tier Compression** (`server/routes.ts:~10455` `/api/quick-upload-dtf`): the OLD code only ran Ghostscript `/prepress` with `-dDownsample*=false`, which barely shrinks raster-heavy DTF (the same 105 MB `AFRICA DAY CT DTF ART.pdf` from enda@tees.ie that crashed the canvas flow ALSO crashed Quick Upload — `/prepress` left it close to original size, the giant base64 string stayed in memory through `JSON.stringify(requestBody)` which makes another full copy of `pdfBase64`, RSS hit 400+ MB, watchdog killed in-flight request → no order). Now: escalate `/prepress → /ebook → /screen` until base64 length ≤ `DTF_MAX_BASE64` (40 MB). After successful shrink, set `req.body.pdfBase64 = undefined` and hint `global.gc()` so the original 100+ MB string is reclaimable BEFORE the next big allocation (the JSON-stringified Odoo request body). Same temp-naming convention as `preShipCompress` (`dtf_gen_in_…`/`dtf_gen_out_…` with random+pid suffix) so the index.ts sweeper picks up any leftovers.

- **OOM Watchdog vs Large PDF Generation** (`server/routes.ts:~1643` post-generation in `/api/projects/:id/generate-pdf`): the memory watchdog at `server/index.ts:131-212` triggers a graceful `process.exit(1)` 3 s after RSS exceeds `MEMORY_RESTART_MB=400`. The robust generator path then does TWO memory-doubling steps before responding: (1) `appendCanvasScreenshotPage` re-loads the buffer into pdf-lib and copies all XObjects, (2) `res.send` queues another Buffer copy in the response stream. Production case: enda@tees.ie / `AFRICA DAY CT DTF ART.pdf` / large_dtf and daragh@hairybaby.com / large_dtf — 105 MB raw PDF pushed RSS to 507 MB, watchdog killed the process before add-to-cart's `compressUntilFits` could ever run → no order, no error, no fallback. Fix: when the generated buffer exceeds 30 MB, run Ghostscript `/ebook` (escalating to `/screen` if still huge) IMMEDIATELY after `generator.generatePDF()` returns, before screenshot append. Raster-heavy DTF compresses >99 % (123 MB → 0.4 MB), so post-compression RSS stays well under the 400 MB ceiling for the rest of the request. Hint `global.gc()` after swap to free the original buffer. Loud `🛟 Pre-ship compression` logs make this visible in deployment logs. Do NOT raise `MEMORY_RESTART_MB` — the watchdog protects against actual OOM-kill by the container; treating the symptom keeps the source memory leak hidden. (Now paired with the **OOM Watchdog Self-Cancelling on Recovery** active gotcha in `replit.md` — when pre-ship compression DOES run but the watchdog has already armed during the un-compressed phase, the recovery check aborts the exit.)

- **Orientation Auto-Switch Uses Source, Not Scaled Element** (`client/src/pages/upload-tool.tsx:~389-525`): the auto-switch between portrait/landscape template variants (e.g. `uvdtf-A3` ↔ `uvdtf-A3-landscape`) MUST compare the LOGO's natural source dimensions (`logo.originalWidth` / `logo.originalHeight`, mm pre-scaling), NOT the canvas element's `width`/`height`. Reason: by the time the orientation effect runs, fit-to-bounds has already scaled the canvas element down — e.g. an A3 landscape PDF (420×297mm) dropped on portrait `uv_dtf_A3` (297×420mm) gets fit-to-bounds scaled to ~217×228mm (slightly taller than wide), which then looks PORTRAIT and matches the portrait template → no switch fires → user sees landscape artwork clipped on a portrait canvas (production: ennis safety / info@esw.ie / esw_eastern_electrical.pdf — user manually rotated 90° + dragged off-canvas trying to recover, then deleted the upload). v1 fix used originalWidth/originalHeight as PREFERRED but fell back to canvas-element dims, which still hit this trap whenever the upload mutation's onSuccess returned the logo record before the deferred `storage.updateLogo` (with originalWidth/Height from PDF MediaBox at routes.ts:~6382) had landed in the React Query cache. v2 (current) REQUIRES `logo.originalWidth && logo.originalHeight` — no element-dim fallback. While waiting, an `orientationCheckTick` state + 400ms `setTimeout` retriggers the effect; a 6s `pendingOrientationCheckStartedAtRef` timeout gives up rather than wedging the pending list. Also added a "source large enough that orientation matters" guard (longest source side ≥60% of template's longest side) so a tiny portrait logo on a landscape canvas doesn't churn the template.

- **OOM Watchdog Self-Cancelling on Recovery** (`server/index.ts:~254-304`, shipped 2026-05-14): the OLD watchdog had two flaws that killed requests AFTER they'd already done the work to free memory. (1) The restart decision at line 264 used the PRE-GC `rssMB` reading, even though the warning branch above had just run GC and computed a post-GC `after` value — so a transient Buffer spike that GC immediately reclaimed still armed the 3 s exit timer. (2) Once `restartScheduled=true` the exit fired unconditionally — no recheck — even if the request that triggered it had since flushed its big Buffer. Production case: banamansales@gmail.com large_dtf 62 MB source `Slovenia2.pdf` — `[MEMORY WARNING] RSS: 494MB → 270MB after GC`, then `[MEMORY CRITICAL] RSS: 494MB — graceful restart in 3s`, then `🛟 Pre-ship (robust) /ebook: 63.3MB → 1.7MB` (the pre-ship compression gotcha worked perfectly), then canvas screenshot appended, then `[MEMORY CRITICAL] Exiting` at +2.3 s — `process.exit(1)` killed the worker BEFORE `res.send()` reached the network. No add-to-cart at Odoo, no order, no error to the customer (per silent-recovery preference). Fix: (a) use `effectiveRssMB` (post-GC value when GC ran, otherwise raw) for the restart threshold check; (b) add a final pre-exit check inside the `setTimeout` callback — if `finalRssMB < MEMORY_WARN_MB` log `memory_recovered`, clear `restartScheduled`, and return without exiting; (c) timer math fix — OLD code used `remaining = Math.max(500, 3000 - 2500)` which always evaluated to 500 ms, so a fast Neon write collapsed the "3 s recovery window" to ~0.6 s. Now tracks `startedAt` before the race and computes `remaining = Math.max(0, 3000 - elapsed)` so the recovery window is actually honored. This preserves the original protection (real sustained OOM still exits) while letting transient peaks resolve. New `memory_recovered` event type is logged to crash_logs for monitoring. Do NOT raise `MEMORY_RESTART_MB` — the container memory limit is the real ceiling; the watchdog still needs to fire for actual leaks.

Anything UNDER those thresholds was routed through `<SvgInlineRenderer>` and dropped into the DOM via `dangerouslySetInnerHTML`. Chromium happily renders ~1500 paths inline, but mid-complexity SVGs (~2 MB / ~2000+ paths) hang the iframe long enough that the surrounding render bails and the browser substitutes its broken-image placeholder — visible result: full grey iframe with a single sad-face icon, no canvas, no toolbar, cart count stays at 0, no `/generate-pdf` or `/add-to-cart` ever leaves the client. Customer impact 2026-05-13: info@esw.ie / `97fab2bf` "uv sticker mirror" — 1.0 MB CMYK PDF → 9.1 MB SVG / 2425 paths / 2837 elements on `uv_dtf_A3`. Deployment logs confirmed upload + preflight succeeded at 7:07:35 UTC then only `/api/version` heartbeats for 2 minutes until the customer abandoned. No server crash (crash_logs untouched for ~10 h), so the new forensics ring correctly stayed silent — this was a pure client render bug. When that low-watermark trips, run `gs -sDEVICE=pngalpha -r{smartDPI}` against the ORIGINAL PDF (NOT rsvg against the heavy SVG — that's the exact thing we're trying to avoid) to produce a `${filename}_canvas_fallback.png`, set `canvasFallbackFilename` + `isComplexVector=true` + `vectorComplexityMetrics.hasUnrenderableContent=true` with `…Reason` text. Color-recolor (`shouldRecolorForInk` / `colorOverrides`) STILL forces SVG rendering by design — if a heavy-SVG customer also enables ink recolor they're back on the inline path; not addressed because (a) the canvas needs the live vectors to recolor and (b) the recolor toggle is opt-in so the user has already gotten past initial render. Loud `🛟 Browser-risk SVG` + `✅ PNG canvas-fallback ready` logs make this visible in deployment logs. Per user preference NO customer-facing warning (would tempt re-add → duplicate orders).
- **Inkscape `--query-all` Root-Element Skip in Upload Bounds Verification** (`server/routes.ts:~5440-5457`, shipped 2026-05-28): customer ticket "Hold On Back" (prod project `1ca086d7-735b-4685-9c94-ad55fc0aea89`, full-A3 PDF with centered Ireland-map raster + "32 COUNTIES" header text + "Don't measure your worth…" footer): output PDF was missing the vector text outside the embedded raster. Root cause was at UPLOAD time, not generation: `gs -sDEVICE=bbox` returns the inked-pixel bbox only (~204×246mm = the raster), the surrounding white/light vector text falls under the bbox device's threshold so it returned only the raster's extent. The existing Inkscape verification at `~5425` (`areaCoverage < 0.92`) correctly fires and runs `inkscape --query-all` to recover that missed content — BUT the parsing loop took the union of EVERY element including the first line, which is always the root `<svg>` (Inkscape names it `svg<n>`). The root's bbox is by definition the geometric union of every descendant including invisible/clipped geometry, so it always inflated the accumulated bbox toward full-page coverage (here 97%). The "background-rect safeguard" at `~5502-5504` (`inkscapeIsFullPage = inkPageCoverage > 0.85 && gsBboxPageCoverage > 0.20` → `shouldTrustGSOverInkscape = true`) then discarded Inkscape's result as "probable invisible background" and fell back to the GS-only bbox — so the very signal that would have recovered the missing text was suppressed by being polluted with the root. Result on disk: `original_width/height = 204.495×245.672mm` exactly matching the embedded image at 363.32 DPI. The downstream tight-crop branch at `~6328` then physically rewrote the SVG to a viewBox cropped to that image bbox, deleting the header/footer text from the canvas-side SVG used for preview AND for PDF output. Fix: in the `--query-all` parsing loop, skip `lineIdx === 0` AND any element whose ID matches `/^svg\d*$/i`. The union of child elements gives the real content bbox — and only TIGHTENS the result vs. the old behaviour (can never lose real content because every visible descendant is still measured individually). For this PDF the union becomes ~77% page coverage, falls below the 85% `inkscapeIsFullPage` threshold, the safeguard correctly does not fire, and Inkscape bounds (~282×369mm) are trusted. Corel-export case (invisible full-page `<rect>` background + small logo) is preserved: skipping the root still leaves the rect in the union, which is still ~full-page, so `shouldTrustGSOverInkscape` still fires and GS bounds still win — no regression. pdf-regression: 8/8 pass. Watch for any new tickets where uploaded canvas dimensions come back unexpectedly LARGER than before — that would mean a previously-suppressed Inkscape result is now winning when it shouldn't.

- **EADDRINUSE Port-Race Fast-Exit** (`server/index.ts:~158-177`, shipped 2026-05-20): production crash_logs showed `listen EADDRINUSE: address already in use 0.0.0.0:5000` recurring every ~6 hours with TWO `server_start` rows (different PIDs, ~15ms apart) immediately preceding — Replit's platform sometimes spawns a duplicate Node process in the same container during rolling restarts/autoscale events, and both race for port 5000. The existing 12×5s retry loop at `server/index.ts:~565` listens via `server.once('error', onError)`, but on Node 20+ `net.Server.setupListenHandle` throws EADDRINUSE **synchronously from inside a microtask** (`processTicksAndRejections`) rather than emitting an `'error'` event — the `once` listener never fires, the throw escapes the Promise executor (which has already returned), and lands in `process.on('uncaughtException')`. Old handler just logged + let the process keep running, but with no listening socket the Replit health check fails ~60s later → customer-visible white-screen in the iframe ("Internal Server Error") while the platform finally kills the zombie. Fix: detect `err.code === 'EADDRINUSE'` at the top of the uncaughtException handler, persist as `port_in_use_lost_race` (distinct event type so it doesn't pollute real crash forensics — real uncaught_exceptions remain alert-worthy) and `process.exit(0)` after the DB write settles. By the time the platform restarts this process, the orphan from the prior container is gone and the port is free. Collapses the customer-visible outage from ~60s to a few seconds. Audit: `SELECT date_trunc('hour', created_at::timestamptz), COUNT(*) FROM crash_logs WHERE event_type='port_in_use_lost_race' GROUP BY 1 ORDER BY 1 DESC` — should show the same ~6h cadence as before but with NO `uncaught_exception` rows for EADDRINUSE.

- **Post-Add-To-Cart Artwork Verification** (`server/routes.ts:~8978-9120`, shipped 2026-05-17): defensive monitoring hook for the "Odoo returns 200 with `order_line_id` but `artwork_files_datas` was never written" failure mode (historical case: order_line 344145 / info@camdenclothing.ie). Fire-and-forget after `res.json(data)` so it NEVER blocks the customer response. We can't XML-RPC into Odoo from this env (no `ODOO_DB`/`UID`/`PASSWORD` secrets, no client) so the only available path is the existing public `/artwork/api/order-pdf/{lineId}` endpoint reusing the customer's `clientCookies`. Body byte length comes from the drained `arrayBuffer()` (`buf.byteLength`) NOT `Content-Length` — chunked-transfer responses have no CL header and would false-positive as 0 bytes, flooding. 401/403 = auth-context drift (common in iframe SameSite sessions where server-forwarded cookies don't carry an Odoo session) → inconclusive, skipped silently. Pure transport errors (fetch throw, status=0) → inconclusive, skipped silently. Forensic row only persists when (a) BOTH probes failed AND (b) `verifyHadAttachmentAttempt` is true — i.e. inline PDF OR offloaded attach-pdf payload OR repeat-order ZIP — so vector-service-only flows don't trigger. Row contains both probe results and pdfPath ('inline'|'offload'|'zip') for triage: `SELECT details FROM crash_logs WHERE event_type='cart_artwork_missing' ORDER BY created_at DESC`. Silent to customer per silent-recovery preference (warning would tempt re-add → duplicate orders). Outer `.catch()` belt-and-braces guarantees the async IIFE can never crash the worker.

- **Raster-Only Fast Path + 180 s Safety Timer** (`server/routes.ts:~1498` safety timer; `~2854-2885` raster-only branch; shipped 2026-05-17): teemaster@serigraf.com / project e163f48a / `Celtic Bag 1.png` (PNG-on-`dtf-large`, 1000×550mm template): `/generate-pdf` hit the in-handler 90 s safety timer and returned 504; empty-cart guard at routes.ts:~8643 correctly refused the add-to-cart. Two stacked causes: (1) PNG uploads have `hasOriginalPDFs=false` (`logos.some(l => l.originalMimeType==='application/pdf')` at routes.ts:~1581), so the request skips BOTH the DTF passthrough at ~1603 and the robust generator at ~1700, falling through to the standard pdf-lib fallback at ~1853. That fallback runs Ghostscript with `-dPDFSETTINGS=/prepress -dColorConversionStrategy=/CMYK -dDownsampleColorImages=false` against the pdf-lib output (~2851-2885) — for a 1000×550mm page with a high-res PNG drawn on garment-colour + white pages, GS re-processes every embedded PNG pixel at native resolution and can comfortably exceed 60 s; combined with pdf-lib `save()` + `appendCanvasScreenshotPage` it blows the 90 s budget. (2) The 90 s timer was set inside the handler while add-to-cart's internal fetch already gives 180 s (routes.ts:~8609), so the in-handler timer was firing strictly before the network ceiling — burning legitimately-completing work. Fix (a): new raster-only fast path in the standard fallback — `logos.every(l => !pdfMimeOrExt && !svgMimeOrExt)` skips the GS `/prepress` CMYK step entirely and emits the pdf-lib bytes (which already wrap the PNG on template-sized pages) straight through `appendCanvasScreenshotPage` → `res.send`. CMYK conversion is semantically pointless for raster-only sources anyway: PNG pixels are RGB, downstream DTF print converts at RIP time, and the user preference is "Core functionality over complex color management features." Mixed/vector flows still hit the GS path unchanged. ## Upstream WAF/Proxy Saga + Upload Bounds — full detail (condensed in replit.md Active, 2026-06)

_Moved verbatim from `replit.md` Active on 2026-06-05 to keep the working file scannable. The condensed Active summary in `replit.md` carries the load-bearing rules; this is the full blow-by-blow for regression debugging._

- **Add-to-Cart Idempotency (safe retry through the WAF)** (`server/routes.ts` add-to-cart handler + `addToCartIdempotency` store above it; `client/src/pages/upload-tool.tsx` `addToCartMutation`, shipped 2026-06-04): same upstream-WAF saga as the upload fallbacks, but on the ORDER-CREATING path. Customer allen@processprint.ie could not add to cart on his network (the owner had to place SO90788 manually). The 3 WAF signatures (403 edge-reject / socket reset / silent HANG) hit add-to-cart too, but unlike `/logos` a blind retry here could DUPLICATE AN ORDER, so retry was previously forbidden. Fix makes retry safe via a **"settle exactly once"** server-side idempotency store keyed by a client `X-Idempotency-Key` (one UUID per click, reused across that click's retries). The FIRST request for a key is the *leader* and runs the single Odoo call; same-key retries either get the cached result or **coalesce** as waiters onto the leader and receive its exact outcome — they NEVER start a second Odoo call, so same-key retries cannot duplicate. `idemSettle(status, body)` (guarded by a once-only `idemSettled` flag) is called at EVERY terminal exit (success 200, 400 missing-id, 503 NO_PDF_SOURCE, non-ok Odoo passthrough, catch-500), caching the outcome and draining all waiters with the same response. **Liveness/memory invariant:** `fetchOdoo()` now has a hard 180s `AbortController` timeout (it had NONE before), so the leader ALWAYS reaches a terminal exit → always settles → waiters never park forever and every entry eventually gets a `result`; the sweep only evicts SETTLED entries past a 10min TTL (+1000 hard cap), never an in-flight leader. Client key length is bounded to ≤200 chars. CLIENT: `addToCartMutation` generates one key per click, retries up to 3× (800ms·attempt backoff) on `{403,502,503,504}` + connection errors/`AbortError` (60s per-attempt `AbortController` = hung proxy); PDF generation stays OUTSIDE the retry loop; client does NOT auto-retry 500 (so a leader that settles 500 surfaces as a hard failure, not a duplicate-causing retry). **Accepted residual (inherent uncertain-commit boundary, NOT a regression):** if Odoo COMMITS but the server fetch is aborted at 180s before the response arrives, the key settles 500 (same-key retries safely get the same 500), but a user *manually* clicking again mints a NEW key and could create a duplicate — only fixable with Odoo-side idempotency (key→order_line map) or a post-timeout reconciliation lookup; deliberately out of scope. Verified: pdf-regression 8/8, edited regions typecheck-clean (project has ~98 pre-existing baseline tsc errors unrelated to this), architect PASS (2nd pass after fixing forever-parked-waiter/immortal-entry findings). Watch deployment logs: a same-key retry should log `♻️ [IDEMPOTENT] ... already settled` or `⏳ [IDEMPOTENT] ... coalescing`. If duplicate ORDERS are ever reported, check whether a 180s Odoo abort preceded a manual re-click (residual above) — do NOT "fix" it by making the client auto-retry 500.

The base64-JSON fallback (decodes → temp files → internal localhost multipart replay) already rescued the MAIN dropzone path, but two OTHER client upload XHRs had NO fallback and died with a bare "Upload failed": the sidebar add-logo mutation (`tools-sidebar.tsx`) and the embroidery-canvas upload (`upload-tool.tsx handleEmbroideryFileUpload`, sends `canvasIndex=1`). If aborts appear WITHOUT a following fallback line, a new upload entry point was added with a raw multipart XHR instead of the shared helper.

- **Distributed-White-Content vs Background-Rect in Upload Bounds Verification** (`server/routes.ts:~5460-5560`, shipped 2026-06-02): customer uploaded an A3 **portrait** PDF (`ElectricReefRawRun.pdf`, MediaBox 837.769×1192.61pt = 295.5×420.7mm) of white/light text + art on a dark garment. Two symptoms: (1) detected content bounds came back as a 294×123mm landscape-shaped strip → most of the artwork cropped out, and (2) the template auto-flipped to landscape. Root cause: `gs -sDEVICE=bbox` reports the **inked-pixel** bbox only — white/light ink falls under its threshold, so it returned just the non-white strip at the bottom of the page. The existing `inkscape --query-all` verification correctly recovered full-page bounds, but the "background-rect safeguard" `shouldTrustGSOverInkscape = inkscapeIsFullPage(>0.85) && gsBboxPageCoverage(>0.20)` (built for Corel exports with an invisible page-sized `<rect>`) was too broad: it fired on ANY full-page Inkscape result and discarded the correct bounds, keeping the wrong GS strip. Fix: full-page-ness alone can't tell a background RECT from genuine distributed white content — use the LARGEST SINGLE ELEMENT. A background rect is ONE element that alone ≈ covers the page (single-element coverage ~1.0); distributed white content is MANY small glyph/path elements whose UNION is full-page but whose largest single member is a small fraction of the page (this file: ~9%). Added `maxSingleElementCoverage = inkscapeMaxElementArea / inkscapeRootArea` (both from RAW `--query-all` px — NOT page-clamped values, since clamping mixes px/pt and corrupts the dimensionless ratio) and gated the safeguard with `dominatedBySingleElement (>0.85)`: `shouldTrustGSOverInkscape = inkscapeIsFullPage && gsBboxPageCoverage>0.20 && dominatedBySingleElement`. Falls back to `true` (old behaviour) if root area couldn't be measured. The root `<svg>` (line 0 of `--query-all`) is skipped from the union bbox but its w,h IS read to compute `inkscapeRootArea`. For this file: largest element ~9% → not dominated → Inkscape trusted → correct 295×420mm portrait, no flip. Corel background-rect (~100% single element) → still trusts GS, no regression. Verified e2e (upload returns 836×1190pt portrait; browser confirms 295.1×420.0mm; no landscape flip) + pdf-regression 8/8 (incl. background-rect fixtures teddy-landscape, waterford-crest) + typecheck clean. Known accepted tradeoff: a single genuinely-huge white compound path (>85% of page) that GS misses would still be treated like a background rect (rare). Watch for new tickets where uploaded canvas dims come back portrait/larger when they should be landscape/small — would mean a correct GS strip is now being overridden.
