# Logo Upload and Design Tool
A full-stack web application for designing and generating production-ready vector graphics of logos on garment templates.

## Run & Operate
- **Run Dev**: `npm run dev`
- **Build**: `npm run build`
- **Typecheck**: `npm run typecheck`
- **Codegen**: `npm run codegen`
- **DB Push**: `npm run db:push`
- **Required Env Vars**: `DATABASE_URL`, `FRONTEND_URL`, `SESSION_SECRET`, `ODOO_URL`, `ODOO_DB`, `ODOO_UID`, `ODOO_PASSWORD`, `GHOSTSCRIPT_PATH`, `INKSCAPE_PATH`, `RSVG_CONVERT_PATH`

## Stack
- **Frontend**: React 18, TypeScript, Wouter, TanStack Query, shadcn/ui, Radix UI, Tailwind CSS
- **Backend**: Express.js, TypeScript
- **ORM**: Drizzle ORM (PostgreSQL dialect)
- **Database**: PostgreSQL (Neon Serverless Driver)
- **Validation**: Zod
- **Build Tool**: Vite

## Where things live
- `client/`: Frontend React application.
- `server/`: Backend Express.js application.
- `server/db/schema.ts`: Database schema definition (source of truth for DB).
- `server/routes.ts`: API endpoint definitions.
- `client/src/theme/`: Frontend theme configuration.
- `tests/`: End-to-end and regression tests.
- `server/health-monitor.ts`: PDF generation health probes.
- `server/robust-pdf-generator.ts`: Core PDF generation logic.
- `server/assets/`: Runtime-required assets (ICC profile `PSO_Coated_FOGRA51.icc`, fallback `Vector_Service.pdf`). Kept here (not `attached_assets/`) so the deployment image can safely exclude `attached_assets/`.

## Architecture decisions
- **Monorepo Structure**: Shared TypeScript types between frontend and backend for consistency.
- **Robust PDF Generation**: Employs Ghostscript, ImageMagick, `rsvg-convert`, and `pdf-lib` for multi-tier PDF conversion, CMYK output, and vector preservation.
- **Dynamic Concurrency Management**: `OperationGuard` limits concurrent heavy operations (PDF generation, file uploads) using cgroup memory monitoring to prevent server overload.
- **Comprehensive Health Monitoring**: End-to-end probes (Light, Stress, Upload) with email alerts and an Admin Dashboard for real-time status.
- **Embedded-PDF Deduplication**: Caches `pdfDoc.embedPdf` results during imposition to drastically reduce output PDF size and avoid Odoo API limits.

## Product
- Logo upload, precise placement, scaling, rotation, and color management on garment templates.
- Multi-page PDF output for single and multi-color orders, CMYK, and applique forms.
- Interactive canvas with multi-select, grouping, shape tools, and dual-canvas mode.
- Preflight checks for print readiness (CMYK analysis, font detection, bounding box accuracy).
- Customer-facing order history, reorder functionality, and support ticket system.
- Integration with Odoo 16 for order management and PDF processing.

## User preferences
Preferred communication style: Simple, everyday language.
Current focus: Core functionality over complex color management features.

## Gotchas

> **Reading order:** Start with **Active**, then **Stable invariants**, then **Resolved**. Active = recently shipped, watch for regressions. Stable = rules current code depends on, don't break. Resolved = past incidents whose fix has been stable in production but the context is preserved here for future debugging.

### Active (recently shipped, monitor in production)

- **Inkscape `--query-all` Root-Element Skip in Upload Bounds Verification** (`server/routes.ts:~5440-5457`, shipped 2026-05-28): customer ticket "Hold On Back" (prod project `1ca086d7-735b-4685-9c94-ad55fc0aea89`, full-A3 PDF with centered Ireland-map raster + "32 COUNTIES" header text + "Don't measure your worth…" footer): output PDF was missing the vector text outside the embedded raster. Root cause was at UPLOAD time, not generation: `gs -sDEVICE=bbox` returns the inked-pixel bbox only (~204×246mm = the raster), the surrounding white/light vector text falls under the bbox device's threshold so it returned only the raster's extent. The existing Inkscape verification at `~5425` (`areaCoverage < 0.92`) correctly fires and runs `inkscape --query-all` to recover that missed content — BUT the parsing loop took the union of EVERY element including the first line, which is always the root `<svg>` (Inkscape names it `svg<n>`). The root's bbox is by definition the geometric union of every descendant including invisible/clipped geometry, so it always inflated the accumulated bbox toward full-page coverage (here 97%). The "background-rect safeguard" at `~5502-5504` (`inkscapeIsFullPage = inkPageCoverage > 0.85 && gsBboxPageCoverage > 0.20` → `shouldTrustGSOverInkscape = true`) then discarded Inkscape's result as "probable invisible background" and fell back to the GS-only bbox — so the very signal that would have recovered the missing text was suppressed by being polluted with the root. Result on disk: `original_width/height = 204.495×245.672mm` exactly matching the embedded image at 363.32 DPI. The downstream tight-crop branch at `~6328` then physically rewrote the SVG to a viewBox cropped to that image bbox, deleting the header/footer text from the canvas-side SVG used for preview AND for PDF output. Fix: in the `--query-all` parsing loop, skip `lineIdx === 0` AND any element whose ID matches `/^svg\d*$/i`. The union of child elements gives the real content bbox — and only TIGHTENS the result vs. the old behaviour (can never lose real content because every visible descendant is still measured individually). For this PDF the union becomes ~77% page coverage, falls below the 85% `inkscapeIsFullPage` threshold, the safeguard correctly does not fire, and Inkscape bounds (~282×369mm) are trusted. Corel-export case (invisible full-page `<rect>` background + small logo) is preserved: skipping the root still leaves the rect in the union, which is still ~full-page, so `shouldTrustGSOverInkscape` still fires and GS bounds still win — no regression. pdf-regression: 8/8 pass. Watch for any new tickets where uploaded canvas dimensions come back unexpectedly LARGER than before — that would mean a previously-suppressed Inkscape result is now winning when it shouldn't.

- **EADDRINUSE Port-Race Fast-Exit** (`server/index.ts:~158-177`, shipped 2026-05-20): production crash_logs showed `listen EADDRINUSE: address already in use 0.0.0.0:5000` recurring every ~6 hours with TWO `server_start` rows (different PIDs, ~15ms apart) immediately preceding — Replit's platform sometimes spawns a duplicate Node process in the same container during rolling restarts/autoscale events, and both race for port 5000. The existing 12×5s retry loop at `server/index.ts:~565` listens via `server.once('error', onError)`, but on Node 20+ `net.Server.setupListenHandle` throws EADDRINUSE **synchronously from inside a microtask** (`processTicksAndRejections`) rather than emitting an `'error'` event — the `once` listener never fires, the throw escapes the Promise executor (which has already returned), and lands in `process.on('uncaughtException')`. Old handler just logged + let the process keep running, but with no listening socket the Replit health check fails ~60s later → customer-visible white-screen in the iframe ("Internal Server Error") while the platform finally kills the zombie. Fix: detect `err.code === 'EADDRINUSE'` at the top of the uncaughtException handler, persist as `port_in_use_lost_race` (distinct event type so it doesn't pollute real crash forensics — real uncaught_exceptions remain alert-worthy) and `process.exit(0)` after the DB write settles. By the time the platform restarts this process, the orphan from the prior container is gone and the port is free. Collapses the customer-visible outage from ~60s to a few seconds. Audit: `SELECT date_trunc('hour', created_at::timestamptz), COUNT(*) FROM crash_logs WHERE event_type='port_in_use_lost_race' GROUP BY 1 ORDER BY 1 DESC` — should show the same ~6h cadence as before but with NO `uncaught_exception` rows for EADDRINUSE.

- **Post-Add-To-Cart Artwork Verification** (`server/routes.ts:~8978-9120`, shipped 2026-05-17): defensive monitoring hook for the "Odoo returns 200 with `order_line_id` but `artwork_files_datas` was never written" failure mode (historical case: order_line 344145 / info@camdenclothing.ie). Fire-and-forget after `res.json(data)` so it NEVER blocks the customer response. We can't XML-RPC into Odoo from this env (no `ODOO_DB`/`UID`/`PASSWORD` secrets, no client) so the only available path is the existing public `/artwork/api/order-pdf/{lineId}` endpoint reusing the customer's `clientCookies`. Two-phase probe: wait 2 s (let Odoo write hooks settle), GET the endpoint, treat 200+≥1024B as OK; on suspicious result (404 / 200<1KB / 5xx) wait +8 s and re-probe before persisting — single-shot would flood `crash_logs` during eventual-consistency windows. Body byte length comes from the drained `arrayBuffer()` (`buf.byteLength`) NOT `Content-Length` — chunked-transfer responses have no CL header and would false-positive as 0 bytes, flooding. 401/403 = auth-context drift (common in iframe SameSite sessions where server-forwarded cookies don't carry an Odoo session) → inconclusive, skipped silently. Pure transport errors (fetch throw, status=0) → inconclusive, skipped silently. Forensic row only persists when (a) BOTH probes failed AND (b) `verifyHadAttachmentAttempt` is true — i.e. inline PDF OR offloaded attach-pdf payload OR repeat-order ZIP — so vector-service-only flows don't trigger. Row contains both probe results and pdfPath ('inline'|'offload'|'zip') for triage: `SELECT details FROM crash_logs WHERE event_type='cart_artwork_missing' ORDER BY created_at DESC`. Silent to customer per silent-recovery preference (warning would tempt re-add → duplicate orders). Outer `.catch()` belt-and-braces guarantees the async IIFE can never crash the worker.

- **Raster-Only Fast Path + 180 s Safety Timer** (`server/routes.ts:~1498` safety timer; `~2854-2885` raster-only branch; shipped 2026-05-17): teemaster@serigraf.com / project e163f48a / `Celtic Bag 1.png` (PNG-on-`dtf-large`, 1000×550mm template): `/generate-pdf` hit the in-handler 90 s safety timer and returned 504; empty-cart guard at routes.ts:~8643 correctly refused the add-to-cart. Two stacked causes: (1) PNG uploads have `hasOriginalPDFs=false` (`logos.some(l => l.originalMimeType==='application/pdf')` at routes.ts:~1581), so the request skips BOTH the DTF passthrough at ~1603 and the robust generator at ~1700, falling through to the standard pdf-lib fallback at ~1853. That fallback runs Ghostscript with `-dPDFSETTINGS=/prepress -dColorConversionStrategy=/CMYK -dDownsampleColorImages=false` against the pdf-lib output (~2851-2885) — for a 1000×550mm page with a high-res PNG drawn on garment-colour + white pages, GS re-processes every embedded PNG pixel at native resolution and can comfortably exceed 60 s; combined with pdf-lib `save()` + `appendCanvasScreenshotPage` it blows the 90 s budget. (2) The 90 s timer was set inside the handler while add-to-cart's internal fetch already gives 180 s (routes.ts:~8609), so the in-handler timer was firing strictly before the network ceiling — burning legitimately-completing work. Fix (a): new raster-only fast path in the standard fallback — `logos.every(l => !pdfMimeOrExt && !svgMimeOrExt)` skips the GS `/prepress` CMYK step entirely and emits the pdf-lib bytes (which already wrap the PNG on template-sized pages) straight through `appendCanvasScreenshotPage` → `res.send`. CMYK conversion is semantically pointless for raster-only sources anyway: PNG pixels are RGB, downstream DTF print converts at RIP time, and the user preference is "Core functionality over complex color management features." Mixed/vector flows still hit the GS path unchanged. Fix (b): in-handler safety timer 90 s → 180 s to match the add-to-cart fetch ceiling — defence in depth for vector flows with legitimately long embed loops (large impositions). Loud `🛟 Raster-only project (N logos) — skipping GS /prepress CMYK` log makes the fast path visible. pdf-regression: 8/8 pass (test 15 `15-a4-uploaded-to-dtf-large-scaled-up.pdf` covers the new branch on a PNG-on-dtf-large fixture).

- **Empty-Cart Guard + Pre-Flight Source-File Scan** (`server/routes.ts:~8643-8691` empty-cart guard; `server/robust-pdf-generator.ts:~686-720` pre-flight scan + `~847-852` summary; shipped 2026-05-15): two related silent failures that produced cart lines with ZERO attached artwork. (1) Empty-cart bug — info@camdenclothing.ie test of project "Explosion" / dtf-large (8 logos + 5 text labels, ~580 KB upload): a Ghostscript `/prepress` CMYK-preserve child got `SIGTERM` from somewhere upstream, the `/generate-pdf` handler couldn't finish before its in-handler 90 s safety timer fired and returned 504, large-format DTF skips the client `pdfBase64` so the client fallback was undefined, the OLD `else` branch at routes.ts:8647 logged `❌❌❌ NO PDF SOURCE` and then PROCEEDED to add-to-cart anyway — Odoo returned 200 / order line 344145 with no `artwork_files_datas`. Fix: refuse the add-to-cart with HTTP 503 `{code:'NO_PDF_SOURCE'}` so the cart line is never created; the client's generic "failed to add" toast tells the user to try again WITHOUT any "incomplete artwork" wording that would tempt a re-click + duplicate order (the gating principle behind the silent-recovery preference is "don't create a half-broken order alongside a fixed one" — here there's nothing to keep alongside, so blocking is correct). Persist an `add_to_cart_no_pdf_source` crash_log row with projectId/projectName/template/productCode/element+logo counts/partnerEmail before returning. `needsServerPdf` already excludes repeat-order/zip and `vector-service` flows so this branch is only reachable when real artwork was expected. NOTE: this only addresses the symptom — root cause (Ghostscript SIGTERM during `/prepress` CMYK-preserve, surfacing as a 90 s `/generate-pdf` safety-timer hit) is still open; watch deployment logs for `gs ... SIGTERM` to identify the killer (OOM watchdog? OperationGuard? per-child timeout?). (2) Pre-flight source-file scan — Replit Reserved VM's `./uploads/` is ephemeral and Dropbox backup was removed (`/dropbox-upload` returns 410 at routes.ts:6863), so a PNG-only upload whose file vanishes before PDF generation has NO recovery path: embed throws ENOENT, retry repeats ENOENT, raster fallback short-circuits (PNG has no PDF source to rasterize via `gs pngalpha`), element is skipped, and the only forensics was an opaque stack-trace blob in `__embedErrors[]`. Scan loops unique `referencedLogoIds` from `data.canvasElements` BEFORE the embed loop, checks `fs.existsSync(uploads/${filename})` AND `fs.existsSync(uploads/${originalFilename})` (only flags when NEITHER exists — `embedRasterImage` already falls back filename → originalFilename, so single-missing-file is fine), stashes `{logoId, filename, originalFilename, filenameExists, originalExists}[]` on `pdfDoc.__sourceFileIssues`. Loud `❌❌❌ SOURCE FILES MISSING` log + included in the post-loop `pdf_embed_incomplete` crash_log details under `sourceFileIssues`. The post-loop trigger condition was widened to fire on `sourceFileIssues.length > 0` even if no skip records emitted (defensive — the embed-loop should still fail, but if some other code path masks the failure the scan's evidence still survives). pdf-regression: 8/8 pass.

### Stable invariants (load-bearing rules — don't break)

- **Add-to-Cart Body Size Alignment**: Client-side `pdfBase64` inline cap (190MB) is strictly below the server's `express.json` limit (200MB) to prevent 413 errors before handler execution. The `PDF_INLINE_MAX_CHARS` (40MB) dictates when PDFs are offloaded via `attach-pdf` due to Odoo's ~40MB body limit.
- **DTF Passthrough Safety Gate**: Fast passthrough (serving original PDF directly) only occurs if source dimensions, canvas element size, position, and rotation precisely match the template and source, otherwise full canvas generation is used.
- **Single Colour Reflective Templates**: These templates (e.g., `reflective-tshirt`) automatically recolor uploaded artwork to silver and use a default grey garment color, with ink panel restricted to silver options.
- **Single Colour Recolour Skip List** (`server/svg-recolor.ts`): only skip true non-paints (`none`, `transparent`, `currentColor`, `url(#…)`). White is NOT skipped — uploaded reverse-out logos (white text/shapes meant for dark backgrounds) must recolour to the chosen ink, otherwise they're invisible on the canvas/preview and the user assumes recolour failed. If a customer ever needs a literal white knock-out, they should use `fill="none"`.
- **Deployment Image Size (8 GiB Reserved-VM cap)**: Replit Reserved VM does NOT honor `.replitignore`/`.deployignore` — the workspace IS the image. Runtime-required CMYK assets (ICC profile, Vector_Service fallback PDF) live in `server/assets/`, NOT `attached_assets/`, so dev-attached samples in `attached_assets/` (PDFs, screenshots) can be pruned without breaking production. `uploads/` is customer artwork written at runtime — must be migrated to Object Storage / Dropbox to permanently solve the size problem on a long-lived deployment.
- **Landscape Template Variant Naming** (`server/storage.ts` template seed data): portrait/landscape template pairs use the `-landscape` suffix on the `id` (NOT the `name`). E.g. `uvdtf-A3` (id) / `uv_dtf_A3` (name) → `uvdtf-A3-landscape` (id) / `uv_dtf_A3_landscape` (name). The client auto-switch logic in `upload-tool.tsx` toggles by appending/stripping `-landscape` on the templateId. Both variants share the same `productCode` (e.g. `CTUVDTFA3`) so Odoo treats them as the same product. When adding a new template that should support orientation auto-switch, ALWAYS create both portrait and landscape variants in the seed data with this naming convention.
- **Canvas Preview Rasterizer** (`server/routes.ts:~1037` `generateCanvasPreviewPng`): `logo.filename` may be a PNG preview (PDF uploads), an SVG, or an image. Always pick the source by extension and only invoke `rsvg-convert` on `.svg`. Feeding PNG to rsvg silently fails per element (e.g. 144× on imposition), wasting ~5s and flooding logs. Also: skip preview entirely when `canvasElements.length > 40` (canvas screenshot already covers it). Per-call rasterization is cached by source path to deduplicate repeated logos in a layout.
- **Crash Forensics Ringbuffer** (`server/request-tracker.ts` + `server/index.ts:~43-72`): the OOM watchdog calls `process.exit(1)` after `RSS > MEMORY_RESTART_MB (400 MB)`, and Replit only retains deployment logs from the *currently running* deployment — so any republish after a crash wipes the evidence. A 50-slot in-memory ring of `{ts, method, path, email, bytesIn, status, durationMs, rssMbAtStart, rssMbAtEnd}` is fed by an Express middleware mounted right after `express.json` so it sees the parsed body (for email extraction). When `persistCrashLog` fires for any forensic event type (`memory_critical` | `memory_warning` | `uncaught_exception` | `unhandled_rejection` | `suspected_crash`) it attaches `{recentRequests, inFlightRequests, activeOpsDetail}` to the row's `details` JSON BEFORE the watchdog's exit timer fires, so the snapshot survives the kill. On next startup the suspected-crash detector hunts the previous instance's window for a `memory_critical` row with forensics and lifts them into the new `suspected_crash` row, so "what crashed it" is answerable from a single DB row: `SELECT details FROM crash_logs WHERE event_type='suspected_crash' ORDER BY created_at DESC LIMIT 1`. Skips chatty endpoints (`/api/version`, `/health`, `/ping`, `/api/analytics/heartbeat`) so the ring stays focused on real work. Bodies are NEVER stored — only `Content-Length` — to keep the tracker itself memory-safe under load. Email extraction order: `X-Partner-Email` header → `req.query.email`/`userEmail` → `req.body.userEmail`/`email` (re-attempted at finish in case body wasn't parsed at request-start time, e.g. multipart uploads).
